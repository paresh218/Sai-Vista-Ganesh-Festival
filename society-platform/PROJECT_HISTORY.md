## Product and technical decisions

Theme preservation is an ongoing acceptance requirement. The original festival site is the visual reference: plum (#641847), gold (#c69b52), cream (#fffaf3), readable plum text, rounded cards, warm hero surfaces and Poppins-style typography. Recreate that identity in the separate app; do not import legacy runtime CSS or change the original files. Use shared theme tokens for public/admin/account flows and future native wrappers. Keep accessible contrast, visible focus and responsive layouts. Public display names, taglines and announcements are configurable locally. Logos, palette controls and festival artwork remain S05/S08 work; do not force Sai Vista branding or a religious symbol onto every community. Poppins is now bundled locally through pinned @fontsource/poppins 5.3.0, including Latin/Devanagari font faces and the original OFL license. System fonts remain a loading fallback; no runtime request to a font CDN is needed.

Build one service used by many communities: housing societies, Ganesh mandals, Durga mandals, festival committees and other community groups. Each gets its own identity, members, admins, settings, events and private records. A person can belong to several communities. Offer one shared store app initially, rather than many near-identical store apps; community branding appears after selection.

Open onboarding: anyone may create a user account. After email verification, a user can find a listed community by name, city and type and request to join; approval remains with that community's administrators. If it is not listed, the verified user may register a new community and become its initial owner through an atomic, backend-validated operation. Registering a new community does not grant rights over an existing one or platform superadmin access. New listings are organizer-submitted/self-declared, not claims of independently verified legal ownership. Exact duplicate-name/location checks are best-effort guidance; concurrent duplicates, disputes, abuse prevention and verified-organizer review need later operational controls before commercial launch. Keep private contact data outside public directory documents.

Use “community/member” in new shared user flows; retain the existing Firestore `societies/{id}` paths and internal compatibility identifiers to avoid an unnecessary data migration. Community type is configurable metadata, not a separate copy of the application. Existing society features and permission boundaries must keep working for all types.

Updated requirement: use a NoSQL database and write a new application based on the current site's behavior. The original site's code, structure and assets stay unchanged. Do not import or execute legacy site files in the new app; reimplement needed behavior in typed modules with tests.

Chosen stack: React + TypeScript + Vite for the shared web/resident/admin application, Capacitor for Android and iOS, Firebase Authentication and Cloud Firestore Standard edition (NoSQL) for identity and records. This replaces the earlier Supabase/PostgreSQL proposal. TypeScript gives shared types and maintainable feature components across the web and native packages; CSS remains appropriate for presentation. A language change alone does not create native builds or guarantee performance.

Folder ownership: `web/src/app` for app composition/routing, `web/src/features/<feature>` for screens/domain logic, `web/src/data` for synthetic fixtures, `web/src/styles` for shared styles, `tests` for app tests, `backend/firestore` for rules/indexes/data contracts and backend tests, `android`/`ios` for generated native projects. Keep features self-contained; add shared helpers only when at least two features need them. App dependencies and lockfile live inside society-platform, separate from the legacy site.

Admin content changes become database writes. The site and apps fetch published content, refresh after an admin save and on return/reconnect, and display a saved/published state. New code, new field types, database changes and native capabilities still require development and releases. Never execute admin-supplied JavaScript or arbitrary HTML as configuration. Cached private records must be cleared on logout and membership removal; offline data must show that it may be stale.

First complete workflow: owner creates a society, invites an admin, admin publishes and pins an event with a registration form, resident joins and registers, admin sees the entry and summary, then archives the event. Ordinary users and society admins must not see or change another society's private data. The verified platform superadmin has explicit cross-society visibility.

## Roles and authorization design

- Platform superadmin (the user): onboard societies, assign initial owners, manage service access and view all societies' application records, settings, members, events, registrations, accounts and media. This replaces the earlier restriction on routine cross-society visibility. Provide a platform dashboard with society selection and cross-society summaries. Visibility does not expose passwords, authentication tokens, signing keys or infrastructure secrets; do not implicitly grant unrelated destructive operations.
- Society owner/admin: view and update only their own society's permitted records, settings and content; invite committee members and publish content. They cannot inspect another society or grant platform privileges. Do not allow removal of the last active owner.
- Event coordinator: assigned event registrations and operational fields only.
- Treasurer: authorized financial records and receipts; other admin rights require a separate grant.
- Resident: their own profile/household and registrations, plus society content allowed by membership.
- Visitor: explicitly published public content only.

Use verified authentication, server-checked memberships and Firestore Security Rules. Never trust a society ID or role sent by the browser. Test rules using direct requests, including users with memberships in two societies. Firebase Admin SDK bypasses rules: privileged server functions must recheck membership and role themselves. Audit role changes, publication, registration corrections and financial edits. Provide owner transfer, invitation expiry, rate limits and administrator MFA before production; verify provider availability/cost before selecting MFA.

Provision the initial platform superadmin through a trusted administrative process tied to the user's verified Firebase UID. Confirm that identity during setup; never infer it from a display name, public email field or demo owner fixture. Store platform authority in a protected server-controlled role source, separate from society membership. No resident, society admin or frontend form may create or elevate this role. Enforce both superadmin access and society isolation in backend rules/services, not just navigation. Log privileged access and role changes without copying sensitive record contents into audit logs. Test revocation and session/cache cleanup; a cached privilege must not retain access after revocation. Existing owner demo accounts are society owners only and are not superadmins.

## Proposed database structure

Plan only; no cloud database has been created. Use `societies/{societyId}` and tenant-scoped subcollections for members, households, seasons, events, content, formVersions, registrations, slotBookings, ledgerEntries, mediaAssets and auditLog. Keep private user profiles separate under `users/{uid}`. Root society documents contain approved public directory information only; private settings need separate protected documents because Firestore reads whole documents. Add collections only when their chunk needs them.

Enforce tenant scope through document paths and validated immutable references. References must stay within the same society, including event/form/registration links. Version document contracts, validate allowed keys/types and add query indexes deliberately. Form answers must reference an immutable form version. Keep roles in protected membership documents. Firestore has no relational uniqueness constraint: use deterministic document IDs and validated transactions for deduplication and capacity. Frontend checks alone cannot prevent concurrent bookings. Store money in integer minor units with currency. Paginate; bound listeners and queries to control read costs. Test indexes and realistic synthetic volume before claiming scale.

Store large audio, photos, video and receipts in object storage, not database rows. Separate public approved assets from private originals and receipts. Use signed access where needed. Default analytics to aggregate counts and avoid collecting unnecessary identifiers. Paginate lists and exports. Benchmark with realistic synthetic volume; a database alone does not guarantee speed.

### Mandatory regression coverage for every feature

User requirement added on 20 October 2026: every implemented feature, behavior change and bug fix must include reusable regression test cases. This applies to all S02–S12 work, including demo behavior, shared logic, UI, backend permissions, data operations and native integration. Tests are part of each task, not a separate optional phase.

- Before implementing a feature, list its expected behavior and regression cases. Cover the normal workflow, validation failures, relevant boundaries, denied permissions and failure/retry behavior. Add tenant-isolation and role tests whenever a feature accesses society data.
- Add or update automated tests alongside the implementation, using the appropriate layer: domain tests, React interaction tests, emulator integration tests and browser workflow tests. Assert user-visible outcomes and persisted data/access rules, rather than copying implementation details.
- For every bug fix, first add a reproducing test that fails on the existing code; fix the defect and verify that the same test passes. Do not weaken assertions, skip failures or change expected behavior merely to make tests pass.
- Keep tests deterministic and repeatable with synthetic fixtures, isolated/reset state and no production credentials or records. Verify that tests do not depend on execution order. Cover loading/error states, duplicate submissions and concurrency where relevant.
- Maintain a coverage register in this file for each feature: behavior/case identifiers, test file paths, run command, latest result and any remaining manual/device checks. A total test count alone does not prove every feature is covered.
- Run the affected regression suites after each change and all applicable app/backend suites before a release. Add repeatable CI execution of the new app and emulator suites before production rollout. Preserve the original site's required checks whenever its affected components are changed.
- For behavior requiring actual hardware, system sleep, push delivery, store review or external playback, keep a repeatable manual checklist with device/version and actual results. Mocks, browser viewport simulation and emulator results cannot substitute for these checks. Automate supported portions and record the remaining limits explicitly.
- Do not mark future implementation tasks complete while their regression cases are missing or failing. If a behavior cannot yet be tested, record the reason and keep its coverage item open. Documentation-only plan changes need no runtime tests.
