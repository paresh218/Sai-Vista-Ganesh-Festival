# Local identity checkpoint (S04 in progress)

Only the Firebase Auth emulator is supported by the new account screen. Default demo mode does not initialize Firebase or accept passwords. Run `npm run emulators`, then `npm run dev:emulator` in a second terminal. Use invented email addresses/passwords only. Verification and reset links appear in local emulator output, never in a real inbox. Sessions use memory and end on reload.

The public event/admin screens remain explicitly synthetic and are not connected to this identity. Email verification grants no society membership or admin rights. Verified users can edit their own minimal profile and request resident membership in a publicly listed society. Active owner/admin members can approve or decline pending residents; Firestore rules deny self-approval and arbitrary role changes; only owner-issued, email-bound invitations can create member/admin access. Membership changes are observed live in the account screen. Revoked access cannot be self-restored. Hosted login/delivery, owner transfer, existing-admin revocation, linked-record deletion, full audit and native session persistence remain pending. Do not publish this as a finished identity system.

Use run-local.cmd for automatic setup, or run `npm.cmd run seed:local` with both emulators running to create two synthetic societies and verified superadmin/admin/owner/resident accounts. The helper has hardcoded loopback endpoints and a demo project ID. It prints test-only credentials; never reuse that password elsewhere. It rewrites only the documented synthetic fixture records, not arbitrary user data. The owner belongs to both societies; the admin and resident initially belong only to Sai Vista. Additional development memberships are preserved. Only the separate superadmin fixture receives a protected platform role. No invitations or real emails are sent. Local records reset when the emulators stop unless a later explicit export is configured.

`npm run test:backend` starts local Auth/Firestore emulators and tests identity lifecycle plus access rules. Java 21+ must be available. A hosted project, billing account and Firebase login are not needed. Test code refuses emulator hosts other than the configured loopback endpoints and uses only a `demo-` project.

Production setup must enable and test email enumeration protection, password policy, authorized domains, verification/recovery links and rate limits. Check current provider costs before choosing MFA or SMS. Account deletion must cover associated documents/assets and retention rules, not merely delete the Firebase Auth user.
